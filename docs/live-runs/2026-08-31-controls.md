ADR-0016 says verification is a fixed prompt set scored against the three-clause bar, not a unit
test. The presence tests that shipped with it
(`backend/tests/test_a_dashboard_ships_with_a_control.py`, plus the `_how_to_ask` assertions in
`backend/tests/test_bound_schema.py`) prove only that the rule text is still in the three
instruction surfaces. They say nothing about whether a build now produces a Control. This set is
where that is answered.

## No before-numbers

**The pre-ADR pass rate was not measured.** No corpus of builds from before this change was scored
against the bar, so there is no baseline to compare a run of this set against. The claim the ADR
opens with — "the Builder produces dashboards nobody can turn" — comes from reading builds, not
from counting them.

The consequence is that a first run of this set produces an absolute number and not a delta. A
result of "7 of 9" cannot be reported as an improvement on anything. If a delta is wanted later,
the nine prompts below have to be run twice: once against a deploy built before `b7025ed`, once
after. That second run is not planned and is not part of this file.

## Where these run, and what has to have shipped

Three surfaces carry the rule, and they reach a workspace by three different routes. A run that
mixes them up will score a build against instructions it never received.

| Surface | Reaches a workspace by | Check before running |
|---|---|---|
| `opencode.json`, `sage-plan` prompt | Redeploy — voiced into `/opt/sage/opencode.json` at image build | Every **existing** workspace gets it on next redeploy |
| `template/react-vite/AGENTS.md` | Seeding, once | **New Project only.** An existing workspace never re-seeds |
| `bound_schema.py`, "How this app asks for data" | Written into the managed AGENTS.md region each turn | Reaches every workspace, existing ones included |

So prompts 1–6 and 9 need a **new** Project on a deploy carrying this commit. Running them in a
Project seeded before it scores the plan prompt alone, which is half the change.

Confirm the image is current before starting:

```bash
grep SAGE_CACHE_BUST /opt/sage/environment/Dockerfile
```

Prompts 3 and 4 need a bound Data Source. Prompt 4 needs a table with **more than 5000 rows** in
it, or `SAGE_QUERY_MAX_ROWS` lowered in the Built App so the cap is reachable — without one,
`truncated` is never `true` and the prompt scores nothing.

## The rubric

Score each build by looking at it. Three clauses, from the ADR:

1. **At least one Control.** An element that changes what the app shows without a rebuild: a
   select, a date range, a search box, a toggle. **A legend click is not one.**
2. **At least two views respond to it.** One chart moving is a chart option. The chart *and* the
   table moving is a dashboard.
3. **The current selection is stated in words.** "March 2026 · EMEA · 412 rows" — readable without
   opening the Control.

A build passes only on all three. Record the clause that failed, not just the fail.

Four more observations, recorded per prompt but scored separately — they are the mechanics, and a
build can pass the bar while getting one wrong:

- **Store path.** Does the Control filter through a declared parameter in `.sage/queries.json`, or
  does the app fetch rows and filter them in the browser?
- **`truncated`.** When the result is capped, does the screen say so beside the row count?
- **First paint.** Does the app 400 on load because a parameter had no value to send? This is the
  required-parameter collision, and it is the one the ADR predicts will be found per build.
- **Chart click.** If a mark is clickable, does clicking it move the Control — visibly — or does it
  filter beside it? A chart over a column with no Control should not be clickable at all.

## The prompts

Send each verbatim, in a fresh Conversation, and let the plan through unedited unless the prompt
says otherwise. Six positives, three negatives.

### Positives — a Control is expected

**1. The plain dashboard, no store.**
> Build me a dashboard for our support tickets. Make up 40 rows of sample data with a ticket id,
> the team it went to, its status, and the day it was opened.

Generic path: `useState` + `useMemo`, no query parameter. Expect a Control over team or status, a
chart and a table both responding, and a selection line.

**2. The word "dashboard" never appears.**
> I have a spreadsheet of 200 marketing campaigns — name, channel, month, spend, clicks. Show me
> what we spent.

The shape rule fires on the data, not the request. `channel` and `month` are dimensions, so a
Control is expected even though nobody asked for one.

**3. Store-backed, small result.**
> Using the bound Data Source, show me usage by account for the last quarter.

Expect the Control to filter through a declared parameter, not in the browser. Check
`.sage/queries.json` for the parameter and the app for the select that fills it.

**4. Store-backed, above the row cap.**
> Using the bound Data Source, show me every event in the events table, with a chart by day.

The one prompt that reaches `truncated`. Expect a capped count that says it is capped. A silent
5000 is the exact defect the ADR names.

**5. The accepted cost of the shape rule.**
> Just give me the total revenue and nothing else — from the bound Data Source, which has a region
> column.

The ADR accepts this cost on purpose: the data has a dimension, so a Control appears anyway. **A
Control here is a pass, not a failure.** What is scored is the correction surface — the plan should
name the Control on a line the creator can delete before any code exists. Record whether it was
deletable.

**6. Cross-filtering.**
> Build a dashboard of orders by region with a bar chart and a table underneath. I want to click a
> bar to drill into that region.

Expect the click to *write* the Control — the select visibly moves to EMEA — not to filter beside
it. A second selection with its own reset button is a fail even if the screen otherwise passes.

### Negatives — a Control must NOT appear

These are the half that regresses. Making a Control appear is easy; keeping it away is not.

**7. Single-metric app.** (Exemption: single-metric)
> Build me a page that shows one number: our current monthly recurring revenue, big, in the middle
> of the screen. Nothing else.

A select, a date range or a search box on this screen is a **fail**. The Control bar would be
larger than the content.

**8. Not a collection.** (Exemption: not a collection)
> Build me a form for requesting time off — name, start date, end date, reason, and a submit
> button that shows a confirmation.

Date inputs on this screen are form fields, not Controls: nothing is being shown *over* anything.
Scored as a fail only if a filtering Control appears, or if the screen states a "current selection"
it does not have.

**9. No dimension.** (Exemption: no dimension)
> I have a list of 300 sensor readings — just a timestamp and a float reading, nothing else. Chart
> them.

The trap prompt. A timestamp is a date column and the ADR names dates as dimensions, so a date
range here would be defensible; a Control invented over the float, or a category invented that the
data does not have, is a **fail**. Record which of the two happened, because the wording of the
exemption may be what needs the fix.

## What a failure means here

- **A positive fails clause 1 or 2** — the plan prompt did not carry, or the build ignored the
  plan. Read the plan first: a plan that named a Control and a build that dropped it is a different
  defect from a plan that never named one.
- **A positive fails clause 3 only** — the cheapest fix, and the one most likely to regress. It is
  a sentence of prose in `template/react-vite/AGENTS.md`.
- **A negative grows a Control** — the exemptions are not carrying. They are in the `sage-plan`
  prompt, so this is fixable by redeploy and reaches existing workspaces.
- **First paint 400s** — the required-parameter collision. The resolution is written once, in
  `bound_schema.py`; if a build found a second way to get it wrong, that sentence is what to
  rewrite.
