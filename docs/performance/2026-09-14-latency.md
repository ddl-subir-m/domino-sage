# Sage latency: measured opportunities, 14 September 2026

The earlier conclusion that model time is irreducible does not hold. Sage can reduce the
number of model calls, the input and output per call, and the wait before output becomes
visible. The serving provider also matters. Changing model weights is not the only option.

This work tests those claims through the user's Domino LLM Gateway. It also implements
connection reuse in both Sage model clients, general-purpose Chat instructions, and Build
source-path context with explicit patch instructions. It does **not** establish that production Sage
now meets a response-time target. The fix is local and has not been deployed.

## What changed

`OpenAICompatibleClient` and `MultiProviderOpenAIClient` previously opened and closed an HTTP
client on every inference. They now keep a bounded connection pool for the client's lifetime.
Scope and handoff calls use the same gateway client, so they can also reuse its connections.
Idle connections expire after 60 seconds. Requests still get fresh credentials and tags;
the pool does not retain response cookies. Concurrent requests can stream at the same time.
The orchestrator and standalone shim close the pool on shutdown.

This removes repeated connection setup across closed and open models. HTTPX documents the
same mechanism in its [client guide](https://www.python-httpx.org/advanced/clients/).

The timing script no longer labels all model time as irreducible, or a historical gateway
round trip as a permanent lower bound. `scripts/latency-probe.py` adds repeatable, checked
synthetic tests with a unique nonce, context size, output size, and optional provider routing.
It never executes the tool that the model returns.

## Measurement limits

- Live Sage was at `5ec4bc2`, with OpenCode 1.18.4. The local change started from `090c6cd`; main at `e4dd8ac` was merged before final verification.
- Gateway source inspected: `etanlightstone/LLM_gateway`, `4387d1b0`, version 2.0.12.
  The live API reported the same version. This is not proof of identical deployment bytes.
- The synthetic probes ran from the developer machine through the same Domino gateway.
  Network savings inside the Domino workspace may be smaller.
- Most comparisons have two samples per condition. They are useful tests of a mechanism,
  not estimates of production p95 or proof of coding quality.
- Copy tests check exact output. Route changes and provider prompt-cache hits remain possible.
  A unique nonce avoids exact response-cache hits; it does not disable provider prompt caching.
- The first argument fragment can be punctuation. The Claude experiment also measures time
  to 100 argument characters. Neither number means a file was written or a preview was ready.
- The signed-in Workbench was inspected. The diagnostic API could not be read through the
  available browser route. No new end-to-end Build waterfall was obtained. Usage data below
  is not a substitute for that waterfall.

Raw synthetic measurements are in [2026-09-14-results.json](2026-09-14-results.json).
No credentials, user prompts, or user source files are in that artifact.

## 1. Connection reuse: implemented

Eight alternating GET requests to the gateway's model-list endpoint used either a new
HTTPX client or one shared client. All returned 200.

| Condition | Time |
|---|---:|
| New client, four requests | 0.658–0.812 s |
| Shared client, initial connection | 0.657 s |
| Shared client, next three requests | 0.270–0.353 s |

This is about 0.3–0.4 seconds less setup per warm request on this network. It is not a claim
of that reduction in every production model call.

Six additional streamed calls used the changed Sage client, alternating sonnet, gpt-5.4,
and Gemma 4 31B. HTTPX connection tracing recorded TCP and TLS setup on the first call only.
All six streams completed without a transport exception. Five returned exactly `READY`.
One Gemma result failed that strict check; its text was not retained in that run. Follow-up
Gemma trials returned `READY` once and `READY.` three times, across output budgets of 16 and
256. Thus the original mismatch is unresolved, and should not be reported as a successful
quality check or blamed on the smaller token budget.

## 2. Input size: a major open-model opportunity

Same copy task and 40 output lines, with a synthetic reference catalog that the task does
not need. These are total streamed-request times, in seconds:

| Model | No catalog, two runs | 450 rows, two runs | 1,800 rows, two runs |
|---|---|---|---|
| Gemma 4 31B | 5.15, 6.11 | 16.23, 14.49 | 18.77; read timeout after 56.04 |
| sonnet | 5.05, 5.37 | 5.15, 5.36 | 6.59, 7.29 |
| gpt-5.4 | 4.63, 3.54 | 3.62, 4.82 | 3.99, 5.92 |

The middle catalog was about 12,000 input tokens for Gemma and 9,500 for GPT. The largest
was about 49,000 for Gemma and 37,000 for GPT. Tokenizers differ.

These observations contradict a blanket claim that input size does not matter. They do
not isolate input size from serving-route variance and cache effects. In particular, the
timeout must remain a failure rather than disappear from a successful-only median.

A trivial live Chat request still sent about 20,400 prompt tokens on its main sonnet call.
That identifies a request worth breaking down into tools, instructions, and history. It
does not prove all those tokens can be removed. The apparent duplicate Chat AGENTS.md
was checked: the generated file is already a stub, so deleting another copy is not a fix.

## 3. Output size: useful, but not sufficient

At 450 catalog rows, reduce the copy task from 40 output lines to four:

| Model | 40 lines, median of two | Four lines, median of two |
|---|---:|---:|
| sonnet | 5.26 s | 4.35 s |
| gpt-5.4 | 4.22 s | 2.11 s |
| Gemma 4 31B | 15.36 s | 16.11 s |

All these returned correct file content. GPT benefited substantially. Gemma's serving wait
was large enough to hide any output saving. Shorter patches and shorter summaries are
worth testing, but cannot be presented as a cure for that provider's long waits. Do not
lower a global output-token ceiling: a truncated tool call causes failures and retries.

## 4. Claude: earlier tool output and an explicit cache hit

The native Anthropic route of the same Domino gateway accepted a system text block with
`cache_control: {"type": "ephemeral"}` and a tool with `eager_input_streaming: true`.
No provider endpoint was called directly. Same sonnet alias, 450 catalog rows, 80 output
lines, alternating control and enabled conditions:

| Condition | Time to 100 argument characters | Total time | Longest gap between frames |
|---|---|---|---|
| Control | 8.34, 7.90 s | 8.47, 8.04 s | 4.09, 4.06 s |
| Cache + eager streaming | 3.33, 3.52 s | 8.30, 7.74 s | 0.58, 1.02 s |

All four returned the expected content and ended with `tool_use`. The second enabled run
reported 11,108 cached input tokens. The first enabled run created that cache, yet still
delivered argument content early. Caching and streaming were enabled together, so this
is not a separate causal estimate for each setting. Total generation time barely changed.

The inspected gateway's OpenAI-to-Anthropic converter reconstructs tool definitions and
flattens system content. It drops these controls. Its stream converter already forwards
`input_json_delta` fragments; it is not itself waiting for complete arguments. The native
route preserves the controls. See Anthropic's
[tool-streaming documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)
and [prompt-cache documentation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

There is a second integration step: Sage's OpenCode event mapper currently ignores
`tool.input.delta`. Earlier gateway fragments alone do not make a visible Sage preview.
Do not execute partial JSON or claim a file exists before the tool completes.

## 5. Gemma routing: no reliable win from a simple setting

The Gemma 4 31B alias uses OpenRouter. Six alternating 450-row, 40-line calls compared its
default route with `provider: {"sort": "latency"}`:

| Routing preference | Total times |
|---|---|
| Default | 26.87, 14.25, 29.66 s |
| Latency | 43.40, 6.31, 13.68 s |

The faster median with latency sorting hides a worse slow sample. It is not enough evidence
to change the alias. Some calls sent only five or six frames; others sent 443. Reported
provider cost and cache fields also varied. That is evidence of variable serving behavior,
not proof of which provider handled each call. Record the actual provider before comparing
routes. OpenRouter describes [provider selection and sorting](https://openrouter.ai/docs/guides/routing/provider-selection).

The alias's response-cache setting is separate from prompt caching. The inspected gateway
does not use its exact response cache for tool requests. Initial repeated text probes did
hit that cache and are explicitly excluded from the comparisons above.

Caller-scoped gateway logs for Build session `ses_f626896c3ffegMGt7Rl9E8XEwm`, from
01:45:44 to 02:05:58 UTC on 14 September:

| Model / component | Calls | Sum of provider-call durations | Median call |
|---|---:|---:|---:|
| Gemma 4 31B | 12 | 629.6 s | 38.5 s |
| Opus-4.8 | 17 | 193.6 s | 7.1 s |
| sonnet / scope | 5 | 13.0 s | See individual usage records |

These sums may contain overlap. They are not the user's total wait. One Gemma call took
181.3 seconds for nine output tokens and roughly 32,500 input tokens. Status 200 and its
duration alone cannot distinguish provider queueing, prefill, reasoning, or retries.

Connection reuse is worth fixing but cannot remove that wait. Moving handoff classification
after Chat completion is also not a new fix: the current code already yields `done` first.

## Larger changes implemented after the initial probes

The code already had distinct Chat and Build agents in one OpenCode process. The shared
process was not, by itself, proof of identical requests. Capturing the actual request showed
that Chat inherited a large installed skill catalogue and coding tools.

### Chat: keep skills and delegation; answer general questions directly

**The blanket Chat tool removal was rejected and is not in the final change.** The experiment
hid `skill`, `task`, and `todowrite`. That removed the entire installed skill catalogue,
including potentially useful data skills, and prevented delegation. Small table tests did
not justify that loss. All three tools remain enabled in the final config and shim.

The final change keeps the general-purpose wording in the Chat template, active config, and
per-turn prompt. It no longer declares every question a data question. File access, Python,
artifact creation, and Live Read remain available. No new tool restriction, loop controller,
or general runtime output validator is introduced. A final capture from OpenCode 1.18.4
confirmed `skill`, `task`, and `todowrite` in the offered tools and `data-table` in the
advertised catalogue when that bundled skill was placed in the fixture. The captured
request was 84,976 bytes; no input-size saving is claimed for the restored configuration.

For future work, OpenCode already loads full skill text on demand, and supports per-agent
skill permissions. The worthwhile target is irrelevant catalogue descriptions and duplicated
instructions, while preserving useful skills and delegation. The bundled `data-table` skill
currently teaches React app tables; Chat's table and chart Artifact rules live in its prompt.
A deliberate Chat skill set needs to match those outputs. This work does not implement one.
See the [OpenCode skills guide](https://opencode.ai/docs/skills/).

The **rejected** experiment changed a local request from 83,991 to 25,543 bytes (70% less).
System-message JSON changed from 64,151 to 13,029 characters. Most of the reduction was this
developer machine's large installed catalogue, not proof of the deployed catalogue's size.
The following observations remain useful evidence about request size, but are **not gains
from the final code**:

| Model | Original profile | Rejected restricted profile | Table check |
|---|---:|---:|---|
| Gemma 4 31B | 67.69 s | 29.77 s | Both correct |
| sonnet | 16.74 s | 14.44 s | Both correct |
| gpt-5.4, warm repeat | 6.72 s | 6.08 s | Both correct |

Each real OpenCode turn read a three-row CSV, wrote North=17 and South=8, and reported a total
of 25. These are single observations, not p50/p95 estimates. Gemma ran new-before-old; sonnet
ran old-before-new. GPT's initial 23.46 s versus 5.44 s comparison included startup in the
first case. A separate process ran a 20.82 s warmup, then the warm pair above. The apparent
fourfold initial gain is not attributed to the profile.

A separate general-question check asked why the daytime sky is blue. GPT, Gemma, and sonnet
answered correctly in at most two sentences with no tools or artifacts. It used the restricted
experimental profile; it is not a live check of the final restored tool catalogue. No live
chart-generation check was performed. Existing chart tests and the final full-suite result
are reported separately; table success alone does not prove chart quality.

### Build: supply exact paths and prevent avoidable patch retries

Before the first Build send, Sage lists up to 60 current-app `src/` paths as a JSON array.
It does not load source contents, attached data, hidden files, or sibling apps. The model can
open relevant files together without a separate path-discovery call. Larger apps get an
explicit truncation note. Follow-up nudges do not repeat the list; a fresh session after a
broken tool call gets the original list again.

The first trial reused a classifier listing with line counts. That format was rejected in
favor of exact JSON strings. More importantly, inspection of actual OpenCode tool records
found invalid patch hunks: Gemma used unified-diff line numbers, and both Gemma and sonnet
omitted the required `@@` line. OpenCode reported success for the latter while the source
stayed unchanged. A filename error mentioned in Gemma's final prose was not the tool error;
the durable tool record showed the patch-format problem.

The Build agent now gets a short valid patch example, a rule to use a bare `@@` hunk marker,
and a request to check the changed lines. This prevents a passing typecheck from being
treated as proof that the requested edit happened. It is an instruction, not a new runtime
semantic validator; models can still fail to follow it.

The fixture changed one TypeScript status label and ran a real TypeScript check. Verification
read the resulting file and checked compilation independently of the model's success text.

| Model | Original baseline | Final paths + patch instructions | Main model calls, baseline → final |
|---|---|---|---|
| gpt-5.4 | 12.93 s, correct | 29.99 s, correct, includes new-process startup | 5 → 4 |
| Gemma 4 31B | 68.08 s, **unchanged file** | 96.01 s, correct | 8 → 5 |
| sonnet | 14.21 s, **unchanged file** | 12.92 s, correct | 4 → 4 |

The rejected first listing trial took 136.85 s on Gemma and left the file unchanged. The
final trial fixed the file correctly on all three models. These results support eliminating
discovery work and failed patch attempts, **not a general Build speedup claim**. Gemma still
spent roughly 29–31 seconds in each of three calls. That is not a snappy small-edit experience.
The final Build changes were tested together; their separate causal effects are not isolated.

The workflow tests used the pinned OpenCode binary, fresh synthetic Git directories, the
repository agent prompts, a copied local TypeScript package, and the production Sage gateway
client forwarding to the user's Domino gateway. The proxy held the model alias fixed, capped
output at 2,048 tokens, removed reasoning-effort overrides, and denied web tools for both
conditions. Title generation was recorded separately with gpt-5.4. These tests did not run
the full Sage mode router, approval loop, Live Read service, preview, or deployment. Tool
results and session history came from real OpenCode. They are stronger than a copy probe,
but do not replace a deployed Workbench comparison.

## Gemini Flash: additional tests requested by the user

The available gateway alias is `domino/gemini-3.7-flash`. Four synthetic tool-copy tests all
returned the exact requested content:

| Input | Two completion times | First 100 argument characters |
|---|---|---|
| Small, 521 prompt tokens | 4.90, 4.80 s | 4.80, 4.71 s |
| Added context, 12,036 prompt tokens | 5.18, 4.84 s | 5.09, 4.83 s |

Each response had only three SSE frames, with useful arguments near completion. This sample
showed neither Gemma's large context penalty nor an early tool-streaming gain.

Real OpenCode workflow checks also passed. The first attempt hit an OpenCode status timeout
during first-session setup, before a main-model response was recorded. It is retained as a
failed setup attempt, not a slow Gemini result. On retry, a cold Chat warmup took 29.46 s.
The warm Chat table runs were 6.71 s with the original catalogue and 8.75 s with the rejected
restricted catalogue. **No Chat speedup in this pair.** The final Build instructions produced
the correct edit in 13.83 s across four main calls, including a re-read and a TypeScript check.

Unlike the earlier workflow series, these Flash workflow requests went through the production
EnforcementShim as well as the gateway client, to preserve Gemini's request handling. The
then-current shim tool filter was held constant across both Chat variants. Thus the pair
compares catalogue/config choices, not every old-versus-new shim behavior. Recorded request
bytes are measured before shim rewriting. These runs precede restoration of the Chat tools;
the final code does not claim the restricted profile's speed or input reduction.

## Work still needed for a consistently fast product

Apply these to the common request path and validate each supported model separately:

1. **Reduce serial model calls.** Measure calls for locating files, reading, editing, checking,
   and closing. Give the agent only the file information needed for the task. Batch independent
   reads and prefer small edits. The current prompt already asks for batching; a prompt edit
   alone needs a measured reduction in calls before it counts as an improvement.
2. **Reduce irrelevant context.** Break the actual 20,400-token simple Chat request into named
   parts, then test removals against tool use and answer quality. For Build, retain relevant
   files and decisions. Do not truncate tool-call pairs or signed reasoning history blindly.
3. **Make cache and streaming capabilities survive the gateway.** Use provider capabilities,
   not hard-coded display aliases. Preserve applicable cache controls and eager tool streaming
   through format conversion. Verify both an actual cache read and early argument delivery.
4. **Make real progress visible.** Carry generation progress from OpenCode to the Workbench.
   Show only what is known at that point. Track first useful text, first completed edit, first
   usable preview, and final completion separately.
5. **Qualify the serving route.** For open models, measure the actual provider, queue wait,
   uncached prefill, cached prefill, and output rate under concurrent load. Compare a stable
   serving route with the current variable route. Keep Domino access and data controls in
   the path. A fast result from another model does not qualify the original model's route.

Suggested initial product targets to test, not achieved results: visible acknowledgement
within 200 ms, useful output within two seconds, and a small verified edit within ten
seconds. Track p50, p95, correctness, and failure rate for each model and workload. A larger
build also needs a separate first-preview target. Report models that miss a target openly;
do not average them into faster models or silently replace the user's choice.

## Verification and remaining work

The connection test failed on the old code for both clients: two calls opened two sockets.
After the fix, 93 focused tests passed across connection reuse, gateway routing, shim
streaming, enforcement, and shutdown. Checks include concurrent requests, changed credentials,
cookie isolation, error responses, and idempotent shutdown. Scoped lint passed.

For the final change, 41 focused tests passed for retained Chat tools, general questions,
source-path privacy and bounds, retry paths, connection reuse, and branded Chat instructions. Nine deliberate in-memory fault
injections made nine tests fail: cookie retention, lost pooling, lost Chat filtering on three
models, forced data framing, omitted source context, repeated context on a nudge, and missing
context after a new-session retry. The three tool-filter plants tested the rejected policy;
the final tests instead require Chat to retain its data skills and delegation tools. No repository file was changed for these fault injections.

Full-suite counts, source hashes, the exact tested tree, and the local commit are recorded in
the [worker report on issue #344](https://github.com/ddl-subir-m/domino-sage/issues/344).
The isolation sequence reproduced seven failures on unchanged files, including with both new
test modules deselected. Five also reproduced on a clean archive of main `e4dd8ac` and are
tracked in [issue #345](https://github.com/ddl-subir-m/domino-sage/issues/345). The other two came
from product nouns added to Chat; those were fixed in the owned prompt files. Whole-backend
Ruff found two pre-existing import-order errors in
`tests/test_a_platform_error_reads_as_a_quotation.py` (lines 127 and 192). That file is identical
to main and was left unchanged. Changed-path lint is checked separately.

No push, shared gateway setting change, or deployment was performed. The remaining items
above still need a matched end-to-end Workbench test and load/quality checks on each model.
The implemented transport and Build changes do not complete all five opportunities. In
particular, the blanket Chat context reduction is withdrawn, earlier native streaming is not
wired into Sage, and provider routing is unchanged.

To repeat the context and output probes, from the repository root:

```sh
python3 scripts/latency-probe.py --env /path/to/backend/.env \
  --models sonnet gpt-5.4 'Gemma 4 31B' --context-lines 450 \
  --output-lines 40 --rounds 5 --output /tmp/latency-450.json
```

Repeat with `--context-lines 0` and `1800`, and then `--output-lines 4`. For an OpenRouter
alias, repeat with `--provider-sort latency`; alternate condition order in a larger test.
Keep timeouts and failed correctness checks in the results. The script uses fresh urllib
connections, so these probes compare model request shapes, not the new Sage connection pool.
